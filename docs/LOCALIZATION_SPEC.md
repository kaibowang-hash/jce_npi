# 语言、翻译与术语规范

## 1. 强制目标

NPI One 必须沿用 Frappe 的语言解析与翻译目录逻辑，并对生产质量施加更严格门禁：

> **英文是唯一源语言；简体中文和繁体中文是完整翻译；同一用户界面不得出现白名单之外的普通语言混用。**

该规则覆盖 React 前端、Frappe 后端、Desk 管理页、通知、邮件、打印模板、导出标题、错误、空状态、帮助和外部门户。

## 2. 源字符串规则

- 源代码、DocType 标签、状态显示名、按钮、帮助和用户消息的源字符串一律使用英文。
- Python 使用 Frappe `_()` / `frappe._()`。
- Frappe JavaScript 使用 `__()`。
- React 只使用本地 `t(source, params?, context?)` 适配器；不得在 JSX/TSX 中直接写任何用户可见文案。
- 传入 `_()`、`__()`、`t()` 的 source 必须是可提取的**英文文字面量**；不得使用运行时变量、中文键、页面路径或数组下标作为翻译键。
- 禁止通过字符串拼接形成句子。必须使用完整句子和受控占位符；源文和译文的占位符数量、名称/位置与转义规则必须一致。
- API 枚举、状态、权限、数据库值和事件类型使用稳定英文代码；翻译只发生在显示层。
- 不把中文译文作为字段名、状态值、权限名、幂等键、接口路径或集成契约值。

## 3. 翻译目录与单一事实源

M0 必须根据实际 Frappe/ERPNext 版本确认翻译工具链和语言代码，并形成 ADR。默认要求：
- 自定义 App 按部署版本采用 Frappe 官方格式：v15 及更早版本通常使用 `translations/<language-code>.csv`；v16 起可使用 Gettext PO/MO，且自定义 App 仍可继续使用 CSV。M0 必须确认部署版本、选用格式、确切语言代码、提取与构建命令；
- CSV 使用 Frappe 当前版本认可的列结构；本规格种子文件采用 `source_string,translated_string,context` 表达意图，实施时以实际版本官方格式为准；
- React catalog 从同一翻译源生成，或由 NPI 领域 API 按用户语言提供；
- Frappe 用户/会话语言是唯一语言来源；不允许浏览器、后端、邮件各自维护互不相干的中文词库；
- 翻译提取、生成、编译和校验必须是可重复命令，并纳入版本控制和 CI。

必须至少支持：
- English；
- 简体中文；
- 繁体中文。

具体 Frappe language code 由 M0 从部署事实确认，不能凭记忆硬编码。确认后同时更新 ADR、catalog 路径、测试矩阵和 `contracts/terminology-allowlist.yaml`。

## 4. React 翻译适配层

`frontend/src/i18n/` 至少提供：
- `t()`：英文源字符串、占位符和可选 context；
- `getLocale()`：读取 Frappe 当前用户/会话语言；
- `setLocale()`：通过受控用户设置 API 更新并持久化；
- catalog 加载、缓存、版本和失效；
- missing translation 明显标记与来源记录；
- locale-aware 日期、时间、数字、金额、百分比、单位和列表格式化；
- 术语白名单与混合语言检查入口。

禁止：
- 在 JSX/TSX 写 `"保存"`、`"Save"` 等显示文字；
- `t('Save') + name` 或把句子拆成多个片段拼接；
- 前端自行判断 `zh` 后手写两套文案；
- 直接调用另一套 i18n 库并建立平行 catalog；
- 在组件内部硬编码第三方组件的默认英文标签。

## 5. 零普通语言混用

### 5.1 简体/繁体中文界面
除以下内容外，普通英文一律视为缺陷：
- `contracts/terminology-allowlist.yaml` 明确标记为 `retain` 的缩写、产品名或标准名；
- 客户/供应商名称、产品名称、零件描述、图纸标题和文件名等业务数据；
- 正式编码、文档号、料号、版本号、用户名、电子邮件、URL 和 trace/request ID；
- 计量单位、化学式和标准符号。

`Tooling`、`Gate`、`Trial`、`Worklist`、`Object Page`、`Workspace`、`Execution Request` 等普通界面名在中文 UI 必须翻译为受控中文，不得依赖其在工程圈常见而保留英文。

### 5.2 英文界面
除业务数据外，不得出现中文菜单、字段、按钮、错误、帮助、通知、邮件和打印标题。

### 5.3 边界示例
- 客户产品名 `Valve Cover` 可出现在中文页面；按钮 `Save` 不可出现。
- 编号 `TL-26018-01` 可保留；字段标签 `Status` 必须显示为中文。
- `NPI`、`DFM`、`EBOM` 等白名单缩写可保留；`Tooling 驾驶舱` 不可作为中文界面标题，应显示“模具开发驾驶舱”。

## 6. 术语治理

- `contracts/terminology-allowlist.yaml` 是“可保留缩写 + 必须翻译术语 + 禁用混合示例”的机器可读事实源。
- 每个领域对象、状态、动作和角色只有一个批准译法；简体与繁体分别维护。
- 修改译法属于 B 类歧义，需要产品/业务批准，并同步更新词表、catalog、截图和自动测试。
- 不允许同一概念交替使用“模具”“工装”“Tooling”，除非词表明确区分业务语义。

## 7. 错误、通知、邮件与打印

- 后端错误返回稳定 `error_code`、占位参数和英文 source message；前端按当前语言渲染。
- 服务器直接生成的通知、邮件和打印模板，按收件人/模板语言调用 Frappe 翻译目录。
- 技术日志使用英文稳定代码；用户界面不显示原始堆栈或未翻译第三方异常。
- 队列、Webhook 和 ERPNext 错误必须映射为已翻译的业务说明，并保留 trace/request ID。
- 导出文件中的列头、工作表名、状态和说明遵循导出请求语言；业务数据本身不翻译。

## 8. 格式化

- 日期、时间、数字、金额、百分比和列表使用 locale-aware 格式。
- 数据库存 UTC，显示遵循用户时区和公司规则。
- 单位符号不翻译；文字单位进入翻译目录。
- 翻译不得改变小数精度、计算、单位换算、ID 或排序规则。

## 9. 缺失翻译策略

- 开发环境：显示明显标记，例如 `⟦Missing: Save⟧`，并记录来源文件。
- 自动测试：本次触及的核心流程要求 100% 翻译覆盖；第三方组件默认标签也计入覆盖范围。
- 生产构建：不得依赖“缺失翻译回退英文”形成混合页面。核心翻译缺失直接阻断构建/发布。
- 新增显示文字必须在同一 PR 提交英文源、简体中文、繁体中文、词表检查和测试。

## 10. 自动门禁

CI 至少执行：
- 扫描 JSX/TSX、Python、Jinja、JSON/YAML 配置中的未包装显示文字；
- 验证 `_()` / `__()` / `t()` 参数是英文文字面量；
- 校验简体和繁体 catalog 的覆盖率、重复项、context 和占位符；
- 扫描中文页面的普通英文残留，并应用 retain 白名单；
- 扫描英文页面的中文残留；
- 扫描同一术语的多译法；
- 运行 英文、简体中文和繁体中文的组件/E2E 冒烟测试；
- 输出新增、删除、未使用和缺失 source 字符串差异。

## 11. 验收证据

每个核心 UI/消息任务至少提供：
- 英文、简体中文、繁体中文截图或 E2E；
- 翻译 catalog diff；
- 硬编码显示文字扫描；
- 三种语言的混用扫描；
- 占位符一致性结果；
- 词表变更（通常应为无）；
- 本次触及核心流程缺失翻译为零的证明。
