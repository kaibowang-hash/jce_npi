# 5. 详细功能需求

以下需求按业务模块编号。P0 为首个可用版本必须，P1 为后续优先，P2 为增强。所有实现必须遵守根目录 `AGENTS.md`、机器可读契约和当前里程碑边界。

2026-07-25 的 V1.2 reconciliation 通过
`docs/V1_2_RECONCILIATION_ADDENDUM.md` 将原 DOCX 的 229 个 ID 全部纳入
机器 Pack。精确原文与验收在
`implementation/V1_2_DOCX_REQUIREMENTS.csv`，历史覆盖分类在
`implementation/V1_2_DOCX_PACK_COVERAGE_MATRIX.csv`。本文件保留原 173
Pack 需求并列出 13 个新增澄清 ID；不得把 consolidated Pack ID 当作删除
原 DOCX ID 的理由。

### 5.3.1 DOCX Tooling 模型、产能与专用导入

`FR-TX-001..018` 按
`implementation/V1_2_DOCX_REQUIREMENTS.csv` 的原文和验收直接生效。
它们要求区分 Part/Requirement/Master/Applicability/Revision/Set/Trial，
逐套及穴位/镶件/多工序追踪，有版本的过程基线与产能情景，以及完整
Tooling List 导入 provenance、校验、图片确认和回滚。详细实施边界见
`docs/TOOLING_LIST_IMPORT_SPEC.md`。

| 需求ID | 优先级 | 新增澄清 | 验收要点 |
| --- | --- | --- | --- |
| FR-TX-019 | P0 | 分离 Customer Standard、TP Trial Actual 和 Approved Process Baseline。 | 复制标准值不能伪装为测量；值、单位、来源、上下文和有效版本完整。 |
| FR-TX-020 | P0 | 使用有版本的 tolerance/rule 计算差值并显示 `not_measured` / `within_tolerance` / `outside_tolerance` / `unavailable`。 | 未经 DR-REC-002 批准，不把任意非零差异自动显示为红色异常。 |

## 6.2 统一消息规范

| 字段 | 要求 |
| --- | --- |
| event_id | 全局唯一；作为幂等键，重复事件不得重复执行业务。 |
| source_system / target_system | 明确来源和目标，便于路由与审计。 |
| entity_type / entity_id | 对象类型、主系统ID、外部系统ID。 |
| event_type | created、updated、submitted、approved、cancelled、released等受控枚举。 |
| business_version | 对象业务版本或modified时间；防止旧事件覆盖新状态。 |
| occurred_at / received_at | 业务发生时间和接收时间；统一时区与UTC存储策略。 |
| payload / payload_hash | 最小必要数据、完整性哈希；敏感字段不进入普通日志。 |
| correlation_id | 贯穿一次业务调用及后续异步处理，用于端到端追踪。 |
| retry_count / status | Pending、Processing、Succeeded、Failed、Dead-letter、Ignored。 |

## 6.3 集成可靠性要求

1. 所有Webhook接收后先写入Inbox表再返回成功，不在Webhook线程中执行长业务。

2. 接口处理必须幂等；通过event_id、业务对象版本和唯一约束防止重复。

3. 每个接口定义超时、重试次数、退避策略、死信、告警责任人和人工回放步骤。

4. 同步API发生部分成功时，采用补偿事务或明确的“待人工确认”状态，不允许静默失败。

5. 每天运行关键对象对账：项目映射、物料/BOM版本、模具资产、质量状态、变更状态和发布文件。

6. 服务账号按接口拆分权限并定期轮换密钥；Webhook使用签名校验；外部调用经过TLS。

7. 禁止任何新系统通过数据库账号直接写入ERPNext；只读报表也优先使用只读副本或受控数据集市。

| 任务/WBS | 业务对象关联、阻断属性 | 详细计划、依赖、Gantt、Kanban | 先选定一方为任务主系统；不允许双向自由编辑日期 |

| 风险/问题 | 业务严重度、门禁影响 | 团队协作和进度 | 重大问题状态由Hub为准 |

# 7. 核心数据模型与编码

## 7.1 核心对象关系

| 主对象 | 子对象/关联 | 关键关系 |
| --- | --- | --- |
| Engineering Project | Project Gate、Deliverable、Task、Risk/Issue/Action、Decision、Handover | 一个项目使用一个冻结模板版本，可关联多个产品和模具。 |
| Part/Product | Design Document、Document Revision、EBOM、ERPNext Item Map | 工程编号可在正式Item Code前存在；发布时建立不可随意变更的映射。 |
| Tooling Development | Tooling Revision、Supplier Milestone、Trial、Tool Defect、Acceptance、ERPNext Mold Map | 开发对象与正式资产分离，但验收后必须一对一映射。 |
| Trial | Parameter Revision、Sample Batch、Defect、Quality Result、Customer Approval | 每轮试模锁定产品、模具和文件版本。 |
| NPI Readiness | Checklist Item、Evidence、Blocker、Pilot Run、Training、Handover | 就绪度是项目当前快照，阶段门通过时保留不可变快照。 |
| Change Reference | Affected Object、Impact Assessment、Implementation Task、Validation、Effectivity | 正式变更编号来自ERPNext，Hub保存工程实施链。 |
| Integration Event | Inbox/Outbox、External ID Map、Retry Log、Reconciliation Result | 支撑跨系统可追踪与对账。 |

## 7.2 建议状态机

| 对象 | 建议状态 |
| --- | --- |
| 项目 | Draft → Proposed → Approved → In Progress → At Risk/On Hold → Closing → Closed/Cancelled |
| 阶段门 | Not Started → In Preparation → In Review → Passed / Conditional / Rejected → Reopened |
| 文档 | Draft → In Review → Approved/Released → Superseded → Obsolete |
| 模具开发 | Planned → DFM → Design → Build/Receive → Trial → Accepted → Handover → Closed |
| 试模 | Planned → Ready → Running → Analysis → Passed / Rework / Cancelled |
| 缺陷/行动 | Open → Assigned → In Progress → Ready for Verification → Closed / Reopened |
| NPI | Not Started → In Progress → Ready with Conditions → Ready → Handover Complete |
| 集成事件 | Pending → Processing → Succeeded / Failed → Retrying → Dead-letter / Replayed / Ignored |

## 7.3 关键编码与映射原则

1. 项目、模具开发、文档、试模、样件、缺陷和变更引用均使用不可重复的系统ID；显示编号可按客户/年份配置。

2. 工程临时零件号与ERPNext正式Item Code分开；一旦发布映射，不允许通过改字段“换号”，应走替代/变更。

3. 外部ID映射表至少包含source_system、entity_type、source_id、target_system、target_id、mapping_status和有效期。

4. 版本号与状态分开：Rev B不等于已发布，必须同时判断Revision和Lifecycle State。

5. 家族模、复制模具和多穴零件必须使用关系表，不把多个零件编码拼接在一个文本字段中。

| --- | --- |

# 8. 角色、权限与审计

## 8.1 建议角色

| 角色 | 主要权限/责任 |
| --- | --- |
| 管理层/项目委员会 | 查看组合、批准重大门禁/预算/豁免、处理升级 |
| 销售/客户经理 | 创建需求、关联报价/订单、维护客户责任界面、协调客户批准 |
| 项目经理 | 项目主责、计划、门禁、风险、行动、移交和结项 |
| 产品/设计工程师 | DFM、图纸、EBOM、设计评审与变更影响 |
| 模具工程师 | 模具方案、设计、供应商、试模、缺陷、验收和资产移交 |
| 工艺工程师 | 机台/材料/参数、试模、试产、能力和作业文件 |
| 质量工程师 | 质量计划、检验结果、NCR、样件/客户批准、PPAP（如适用） |
| 采购/供应链 | 供应商、报价/PO、交期、收货、成本和供应准备度 |
| 生产/维护 | 量产就绪、培训、现场文件、模具维护和在产反馈 |
| 文控 | 编号、版本、发布、撤回、外部分享和归档 |
| 财务/成本 | 预算、承诺、实际、资产化和项目结算 |
| 供应商用户 | 仅访问授权项目/模具的里程碑、文件、问题和整改 |
| 客户用户 | 仅访问授权资料、样件/文件审阅、批准和反馈 |
| 系统管理员/集成运维 | 配置、权限、接口监控、回放、审计和升级 |

## 8.2 权限模型

1. 采用角色权限 + 项目成员 + 客户/供应商范围的组合控制；默认拒绝，按最小权限开放。

2. 外部用户与内部用户分组隔离，不允许外部账号浏览全局客户、供应商、物料或其他项目。

3. 受控文档、阶段门、ECN和质量批准支持职责分离；必要时禁止创建者批准自己的记录。

4. 已提交/已批准记录不得物理删除；更正通过修订、取消、替代或受控管理员操作完成。

5. 高敏感项目可设置保密组、禁止下载、动态水印或仅在线预览。

6. API服务账号不允许交互登录，按接口拆分权限，并记录所有调用用户和来源IP。
